# Test Reference

> The living map of this project's test suite — what is covered, how tests authenticate,
> and what is deliberately not covered. Read this before writing any test, so the suite is
> extended rather than re-derived.
>
> **Rules:**
> - Update this file in the same task that adds, removes, renames, or skips a spec — never as a follow-up
> - Every flow in `docs/agent_context/CORE_FLOWS.md` needs a row in the Flow Coverage Map — a flow with no row is untested, and that must be visible at a glance
> - Permission-gated elements are asserted absent from the DOM in two parts — prove the page rendered, then assert `toHaveCount(0)` — through `expectAbsent` from `e2e/support/permissions.ts`. Never `toBeDisabled()`, never `not.toBeVisible()`, and never a bare absence assertion, which passes on a page that never rendered
> - Query by accessible role and name first — `getByTestId` only for elements with no accessible identity, and only once registered in the Selector Registry
> - Nothing sits in Quarantine without a fixing issue number
> - Anything not yet known at onboarding time is marked as `[TBD]` — fill it in as the suite grows

## Test Auth Strategy

*Populated during onboarding from Section 4c of `docs/agent_context/ONBOARDING.md`.*

| Setting | Value |
|---|---|
| Auth provider | [TBD] |
| Sign-in mechanism | [TBD] |
| Roles with a storage-state fixture | [TBD] |
| Storage-state directory | `e2e/.auth/` |
| Refresh cadence | Regenerated by the Playwright setup project on every run |
| Test user source | Fixed users, one per role, created by hand in the auth provider |
| Credentials file | `.env.local` — `E2E_ADMIN_EMAIL`, one `E2E_[ROLE]_EMAIL` per additional role, and `E2E_USER_PASSWORD` |

**Rules:**
- Authenticate once per role in the setup project — never drive the sign-in UI inside a flow spec, unless the flow under test is sign-in itself
- A spec declares the session it needs at file level with `test.use({ storageState: storageStateFor('ROLE') })`, imported from `e2e/support/auth.ts`. A spec that declares nothing runs signed out — no project sets a default `storageState`, so the default is fail-closed
- One storage-state file per role, named after the role — `e2e/.auth/[role].json`
- Test users are fixed and reused by every run. Never derive a per-run address — it names a user nothing creates, so the setup project fails on the first sign-in and every dependent project is skipped
- Test users are shared, including by concurrent CI jobs. Every test scopes its own data with a unique per-test identifier derived from `testInfo.testId` and asserts only against records it created — no test may treat its user as private
- Full per-run isolation means seeding and deleting users through the Clerk Backend API. That is a deliberate addition to the harness, not the default
- Credentials live in `.env.local`, which is what the Clerk setup helper reads. Nothing in the harness loads `.env.test`
- `e2e/.auth/` is gitignored and is never committed — a storage-state file holds a live session credential
- Never cache storage state between runs or across days — sessions expire, and a stale file produces confusing mid-suite auth failures
- The auth provider is swappable. Clerk is the documented default, not a hard dependency — provider-specific calls live behind the fixture layer in `e2e/support/`, so a swap touches one file
- Never query the database to give a test its role — roles live in the auth provider, per `docs/agent_context/PERMISSIONS_REFERENCE.md`

## Flow Coverage Map

> One row per flow in `docs/agent_context/CORE_FLOWS.md`. A flow with no row is untested.
>
> **Which flows get an end-to-end spec** is decided at onboarding (Section 4c of
> `docs/agent_context/ONBOARDING.md`) and recorded in the End-to-end column, `required` or
> `not required`. Only the developer changes it, and a flow added later gets its value from
> the developer when its row is added. A flow marked `not required` is still proven by the
> tests its tasks' acceptance criteria call for.

| Flow | End-to-end | Spec file | Roles covered | Status |
|---|---|---|---|---|
| *[`[AREA]-1` — Flow name]* | *[required / not required]* | *[`e2e/specs/[area]/[flow-id]-[short-slug].spec.ts`]* | *[[ROLE_1], ADMIN]* | `[ ]` |

**Status legend:** `[ ]` no spec · `[x]` covered and passing · `[~]` partial — criteria still unproven · `n/a` end-to-end not required

**Rules:**
- One directory per application area under `e2e/specs/` — the directory name matches the area name in `CORE_FLOWS.md`
- A spec is named `e2e/specs/[area]/[flow-id]-[short-slug].spec.ts` — the flow ID first, then an optional short descriptive slug. The filename never carries a role. What decides whether a spec runs is its directory: each Playwright project collects a plain `**/*.spec.ts` under its own directory, so a spec placed outside `e2e/specs/`, `e2e/permissions/` or `e2e/a11y/` belongs to no project, never runs, and the suite still reports green
- The Roles covered column records what each spec declares with `test.use({ storageState: storageStateFor('ROLE') })`. A spec covering two roles is two spec files — record both rows
- A flow is `[x]` only when every step and every UI state in its entry has an assertion — a spec that walks the happy path alone is `[~]`
- Every page a flow renders needs an axe scan in `e2e/a11y/`. axe is the automated gate, and automated scanning catches only a portion of WCAG issues — keyboard and screen-reader checks stay manual, per `docs/general_docs/ACCESSIBILITY.md`
- Deferred flows get a row with status `[ ]` and a note naming the phase — do not omit them, or the gap becomes invisible

*Populated during onboarding from Section 4c of `docs/agent_context/ONBOARDING.md`, one row per flow. A flow added later gets its row in the task that adds it.*

## Permission Matrix Coverage

> Mirrors the Permission Matrix Summary in `docs/agent_context/PERMISSIONS_REFERENCE.md`.
> Every row there needs a generated spec here, and every forbidden route needs a status assertion.

| Permission rule | Spec file | Roles asserted | Status |
|---|---|---|---|
| *[Action 1]* | `e2e/permissions/permission-matrix.spec.ts` | *[[ROLE_1] ✓, [ROLE_2] ✗]* | `[ ]` |

**Forbidden routes:**

| Route | Role denied | Spec file | Status |
|---|---|---|---|
| *[`/config/*`]* | *[Non-ADMIN]* | `e2e/permissions/permission-matrix.spec.ts` | `[ ]` |

**Rules:**
- The whole matrix, forbidden routes included, lives in one file — `e2e/permissions/permission-matrix.spec.ts`. `test-author --permissions` regenerates that file wholesale, so hand edits to it are lost. Anything hand-written belongs in a flow spec
- Each role's `describe` block selects its own session with `test.use({ storageState: storageStateFor('ROLE') })`. The block asserting signed-out behaviour declares nothing
- A permitted action is proven by performing it. A prohibited action is proven with `expectAbsent`, which asserts the page rendered and only then asserts the control has count zero — a bare absence assertion also passes on a 500, on an empty error shell, and on a redirect to sign-in, so on its own it cannot tell a working gate from a broken page
- Never assert that a gated element is disabled or not visible — both pass against a correct implementation and against one that renders the element anyway, so they prove nothing about the rule they claim to prove
- A forbidden route spec must assert the response status is 403 and that no redirect occurred — a spec that only checks the page "looks blocked" cannot tell a 403 from a redirect
- Every role in the matrix needs a positive and a negative assertion — covering only the permitted path is not coverage
- Regenerate this table whenever a role or a matrix row changes in `PERMISSIONS_REFERENCE.md` — a permission change with no spec change is a silent regression

*Populated once roles are defined during onboarding.*

## Fixtures and Seed Data

*Fixtures will be documented here as they are added.*

**Rules:**
- End-to-end fixtures live in `e2e/support/`; unit and integration helpers live beside their tests in `tests/` — never in `lib/`, which application code imports
- Seed data must be idempotent — a run that fails halfway must be re-runnable without manual cleanup
- Never assert against data a fixture did not create — a spec that depends on whatever happens to be in the database is not a test
- Never mock the database, the auth provider, or a Server Action in an end-to-end spec — mock only third-party services that charge money or send messages
- Record every test-only environment variable a fixture reads, in `.env.example` and in the Required Variables table of `docs/general_docs/TECH_STACK.md`. The name goes in `.env.example`; the value goes in `.env.local` and is never committed

## Selector Registry

> Every `data-testid` in use, with the reason its element has no accessible identity.
> Keeping the list visible is what keeps it short.

| `data-testid` | Element | Spec files | Why a role-based query is impossible |
|---|---|---|---|
| *[`revenue-chart`]* | *[Chart canvas]* | *[`e2e/specs/[area]/[flow-id]-[short-slug].spec.ts`]* | *[Canvas exposes no role and no accessible name]* |

**Rules:**
- Query by accessible role and name first — `getByRole`, `getByLabel`, `getByText`. `docs/general_docs/ACCESSIBILITY.md` requires an ARIA role and label on every component, so a role-based query doubles as an accessibility assertion
- `getByTestId` is permitted only for an element with no accessible identity — a chart canvas, a map container. The spec must carry a one-line comment stating why
- A `data-testid` is not in use until it has a row here — an unregistered test id is a review failure
- Never add a `data-testid` to work around a missing label — add the label instead, and the component becomes testable and accessible in one change

*Empty on a fresh clone. Every row added must include its justification.*

## Quarantine

> Skipped, flaky, and known-failing specs. This table must be empty before a phase is marked complete.

| Spec | Reason | Quarantined on | Fixing issue |
|---|---|---|---|
| *[`e2e/specs/[area]/[flow-id]-[short-slug].spec.ts`]* | *[Flaky — races the toast dismissal]* | *[YYYY-MM-DD]* | *[`#123`]* |

**Rules:**
- Nothing enters quarantine without an open GitHub issue that will fix it — an entry with no fixing issue is abandoned work pretending to be tracked
- Quarantine with `test.skip` and a comment naming the fixing issue number — never delete the spec, and never use `.only` to route around a failing neighbour
- Never widen a timeout, loosen an assertion, or edit application code to turn a failure green — that converts a visible failure into a silent one
- A row is removed only after the spec passes three consecutive full-suite runs
- Report the quarantine count in Current Coverage at the end of every session

*Empty on a fresh clone.*
